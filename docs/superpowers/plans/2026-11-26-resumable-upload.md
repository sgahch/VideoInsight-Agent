# 音视频分片上传实施计划

> 按 executing-plans 在当前工作区实施。用户已要求开始；保留现有未提交修改，不创建提交。

**Goal:** 原上传入口支持分片、重试、暂停、刷新后续传，校验成功后只创建一次分析任务。

**Architecture:** 沿用 FastAPI、SQLite、本地磁盘。每次上传使用独立 SQLite 会话数据库和目录，事务串行化同一上传的写入及完成请求，其他上传互不阻塞。上传 ID 同时作为最终任务 ID，使任务已持久化但完成响应丢失时仍可恢复；queued 任务继续使用现有启动对账。

**Tech Stack:** Python / FastAPI / sqlite3 / 原生浏览器 JavaScript / pytest / node:test。

## 约定

- 每片默认 4 MiB，客户端最多 3 片并发，失败最多重试 3 次；单片请求有独立超时。
- 上传前逐块计算完整 SHA-256，内存使用不随文件体积增长；重新选择的文件必须匹配完整指纹才能续传。
- 会话保留 24 小时，每个身份最多 4 个未完成上传，未完成文件声明总大小最多为单文件上限的 2 倍。
- 会话、分片、完成、取消均使用现有账号/客户端归属与全局鉴权；不持久化模型密钥。
- 暂停保留分片，取消删除分片。刷新后提示重选原文件；本地仅保存会话标识和文件元数据。
- 新接口 POST /uploads、GET/DELETE /uploads/{id}、PUT /uploads/{id}/chunks/{index}、POST /uploads/{id}/complete；保留 /analyze-file 兼容性。
- 完成时按序校验分片、大小和整文件 SHA-256。队列满时保留分片，允许稍后重试完成。
- 上传文件位于 tmp/_uploads 下，过期回收接入现有启动和周期性清理；分析文件仍放 media/{task_id}。
- 当前部署仍采用已有单服务任务队列；不引入对象存储、Redis 或分布式调度。

## Review focus

分片请求响应丢失时幂等；同一上传同时完成；任务创建后会话提交前进程退出；清理不能删除活动上传；恢复不能把相同文件名的不同内容混在一起；失败不能丢失用户模型配置或泄漏密钥。
